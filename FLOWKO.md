# Flowko fork of Cal.diy

This repository is Flowko's fork of [Cal.diy](https://github.com/calcom/cal.diy), the MIT community fork of Cal.com, self-hosted at https://booking.flowko.si.

## Upstream

Synced to `calcom/cal.diy` commit `e8afecd163` (2026-11-03, "fix(bookings): send notification emails when calendar integrations fail (#30434)") by a merge commit (U16, 2026-11-03); first pinned to `54343aa685ae8f33159d2f485ec4a57bad5c574a` (2026-09-20). The `flowko` branch is upstream plus the changes below.

**How to sync upstream again:** merge, never rebase or cherry-pick. `flowko` is public and live, image tags are fork commit SHAs and this file cites fork commits. Work on a branch `sync/upstream-<sha>` in its own worktree with its own `yarn install` (never in the main checkout first: other worktrees symlink its node_modules). `git merge --no-ff upstream/main`, resolve keeping every change listed below, put Flowko's refusals of new upstream behaviour in separate commits with tests, run the gate, then merge into `flowko` with `--no-ff`. Watch for upstream code that reaches event contents, tokens, the booker's data or new sign-in paths without a textual conflict (U16 found one). Undo on `flowko` with `git revert -m 1 <merge>`, never a reset; the next sync then needs that revert reverted first.

## Changes vs upstream

Lines marked *planned* are not on `flowko` yet; each is updated when its change merges.

  - *Public booking response (`f5e95b2`):* `/api/book/event` and `/api/book/recurring-event` pass the booking service's result through `toPublicBookingResponse` (`packages/features/bookings/lib/publicBookingResponse.ts`), an allow-list of what the booker UI, the success redirect and the embed events read: uid, title, description, times, location, status, `eventTypeId`, responses, the organizer's name and time zone (never the e-mail), the attendees whose e-mail the booker entered, `paymentRequired`, `paymentUid`, `seatReferenceUid`, `isDryRun` and the decoy flag. Since U8e a dry run by anyone but a host skips that lookup (U8e *e*).

An ADMIN signed in as `INACTIVE_ADMIN` (no 2FA, or a weak password) is not an admin on the server. That covers the webhook router, `availability.user`, the Zapier/Make subscriptions, `isAdminMiddleware`/`authedAdminProcedure`, and the admin and webhook settings pages. The route acts as the booking's organizer, and every bad token gets the same answer, so there is no padding oracle. Links in emails sent before U8c no longer work. Since U8e it acts only on a pending booking, and since U8f only on a POST from the confirm page `/booking/link`; a GET opens that page (see U8f).

    - `IP_BANLIST` must be a JSON array or unset, and it has no effect on callers that hash their identifier.
    - `NEXT_PUBLIC_IS_E2E` turns the limiter off (with the admin 2FA rule and Turnstile) and must never be set on Railway.

    - `publicViewer.markHostAsNoShow` only reports a host no-show, only on an accepted booking that has started, and is limited per IP.

- **U8e Last hardening pass before the first client** (David, 2026-09-27; the leftovers of the U8 re-attack on `d48a666`, notes a to g):
  - *Booking errors keep their status:* `packages/lib/fetch-wrapper.ts` (createBooking, createRecurringBooking) gave `HttpError` a spread copy of the Response. A Response keeps `status` and `url` in getters on its prototype, which a spread doesn't copy, so every error had `statusCode` undefined and no url, and a body that was not JSON (a proxy's HTML 502) threw a SyntaxError. The HttpError now carries the status, the url (the request's when the answer has none), the method, the body's `data` and the body's `message` (else the status text). `isRateLimitError` still also matches the message, because next-auth errors and plain JSON bodies carry no status. Test: `packages/lib/fetch-wrapper.test.ts`.
  - *Rate limits per limiter* (the in-memory store in `packages/lib/rateLimit.ts`; replaces U8c's single budget): a namespace is one call site's limiter, its rate-limiting type plus the word labels in front of the identifier (`getRateLimitNamespace`: `core:login`, `core:emailVerifyCode`, `core:api:cancel-ip`). A hash, id, IP address or e-mail ends the prefix, and the last segment never counts.
    - Each namespace holds at most 50,000 live windows, the old global cap. All namespaces together hold at most 100,000, but each namespace keeps a reserve of 1,000 that the store-wide cap never takes. There are at most 64 labelled namespaces; a later one counts under its type alone.
    - A new identifier that finds no room shares its own namespace's overflow window: still fail closed, and no live window is evicted. So a flood of fresh identifiers at one limiter (random e-mails at the sign-in check from one IP at about 833 requests a second, or at the email-code check from many IPs, since that check allows one IP 10 a minute) degrades only that limiter. Before, it sent every new identifier of every other `core` limiter (a host's first sign-in, a new booker) into one overflow window that the flood kept used up.
    - Memory: one window is about 330 bytes, one full namespace about 16 MB, the worst case about 57 MB (100,000 windows plus every namespace's reserve).
    - Residual: inside its own namespace a flood still denies new identifiers for up to a minute. Since U8f a per-IP sign-in limit (30 per 60 s) caps what one IP can add to the sign-in limiter, so a sign-in flood now needs many IPs (see U8f).
    - Test: `packages/lib/rateLimit.test.ts` ("per-namespace budgets").

- **U9 Unreadable Google calendars fail closed**: a calendar Flowko can't read is unknown, not free.

- **U9 Tokens encrypted at rest**: Google's OAuth policy requires OAuth tokens encrypted at rest. Upstream kept the token object in plaintext in `Credential.key`. Its optional keyring copy in `encryptedKey` swallowed encryption errors, and its only decrypting reader fell back to the plaintext key.
  - *Storage:* a `google_calendar` credential (and `google_video`, if it is ever enabled) keeps `{"_enc":"keyring-v1"}` in `key`, and in `encryptedKey` the JSON of an AES-256-GCM envelope `{v:1, alg:"AES-256-GCM", ring:"CREDENTIALS", kid, nonce, ct, tag}` (base64url; 12-byte nonce, 16-byte tag) of the token object. The AAD binds the purpose `Credential.key`, `type`, `userId` and `teamId` (built only by `credentialKeyAad()`), so an envelope copied to another row or tenant fails authentication. Envelopes are validated (v, alg, ring, an upper-case kid, nonce and tag lengths) before any key material is read. `schema.prisma` is unchanged; plaintext rows are refused, never read as a fallback, and never migrated.
  - *Where tokens are decrypted:* only in `CalendarAuth` (lazily, when a Google call needs them) and at the revoke and account-lookup sites of `handleDeleteCredential` and `replaceEarlierCredentials`. The code is in `packages/features/credentials/services/CredentialDataService.ts` and `packages/lib/crypto/keyring.ts`. The refresh write-back re-encrypts with the CURRENT kid (`CredentialRepository.updateEncryptedKeyWhereId`). It binds the envelope to the row's type, userId and teamId as it reads them just before the write, not to the fields the token was decrypted under, and writes only while the row still has them. A DB write that re-points a row to another user between that read and a refresh would store the old owner's refreshed token, encrypted for the new owner, in that row; this is an accepted risk, because it needs DB write access and a race. No token is copied back into an in-memory `credential.key`. The fail-open decrypt in `getCalendarsEvents` is gone. `updateTokenObjectInDb` also serves the disabled pipedrive app, which would now store an encrypted key its own reader can't use.
  - *Fail closed:* every failure raises `CredentialKeyUnavailableError` with a reason: `keyring_not_configured` or `decrypt_failed` (transient), `not_encrypted` or `malformed_envelope` (permanent). It is logged once per credential and reason every 5 minutes as `Credential key unavailable (<reason>) for credential <id|new> (<type>)`, with the credential id, type and reason and the envelope's kid (a new credential's line carries the userId instead). The kid is not secret. The line never carries a token, the envelope's nonce, ciphertext or tag, an env value or an error object. A key failure never marks a credential invalid and never sends the broken-connection e-mail.
    - Connect: `add` answers 503 before Google's consent screen, and the callback answers 503 before the code exchange. ## API v2 must not be deployed

The image builds only the web app (`./Dockerfile`); `apps/api/v2` (the `calcom-api` service in `docker-compose.yml`) is not part of the deployment and must stay out of it. Flowko's booker-facing fixes were made on the web app's routes and pages, not on API v2. There, `GET /v2/bookings/:bookingUid` (2024-04-15, no auth guard on the route) returns every seat's reference, and the 2024-08-13 `GET /v2/bookings/:bookingUid` and `/v2/bookings/by-seat/:seatUid` (optional auth) return every attendee's `seatUid` when the event type shows attendees. A seat's reference cancels that seat through `POST /v2/bookings/:bookingUid/cancel`. Deploying API v2 first needs an auth guard on those routes, or their output limited to the caller's own seat. It would also reopen U8c fixes that live only on the web app's tRPC routes: API v2 has its own SelectedSlots writers (slot reservation, AV-2) and accepts the internal `getSchedule` flags (AV-5), and its throttler keys on the client-sent `cf-connecting-ip` (`apps/api/v2/src/lib/throttler-guard.ts`).

## Calendar-subscription features must stay off

Keep the `calendar-subscription-cache` and `calendar-subscription-sync` features off (Settings → Admin → Features, `/settings/admin/flags`). When they are on, `packages/features/calendar-subscription/adapters/GoogleCalendarSubscription.adapter.ts` calls `events.list` on the selected calendars and stores the summary, description and location of every event. It is the only reader of event contents, so turning it on makes the connect notice ("does not read the contents of your other events"), the Google Calendar app descriptions (English and Slovenian) and section 3.3 of the privacy policy false. `SELECT slug, enabled FROM "Feature" WHERE slug IN ('calendar-subscription-cache','calendar-subscription-sync');` must return no row with `enabled = t`.

## Rebuilding the image

Every push to `flowko` runs `.github/workflows/build-image.yml` on a GitHub-hosted `ubuntu-latest` runner. Once `flowko` is the default branch, it can also be run by hand from Actions → Build image → Run workflow on `flowko` (any other branch is skipped). It pushes:

- `ghcr.io/davidvojvodic/flowko-booking:<commit sha>`, which is the tag to deploy
- `ghcr.io/davidvojvodic/flowko-booking:flowko-latest`

The workflow does not boot the image before pushing it (upstream's release pipeline does), so `flowko-latest` is untested. Deploy only a `<commit sha>` tag that has been started and checked.

**Railway health check (set 2026-11-04, U19):** the `web` service has `healthcheckPath=/api/version`, `healthcheckTimeout=300` and `overlapSeconds=20` (set with `railway api` `serviceInstanceUpdate`, read back). **Runtime variables and Turbo (U22):** every new runtime variable must be added to `turbo.json` `globalEnv` (secrets that must stay out of task hashes: `globalPassThroughEnv`, as the keyring). The container starts the app with `turbo run start` in strict env mode, which passes the Next server only the listed variables; an unlisted one is undefined there even though Railway sets it.

The `NEXT_PUBLIC_*` values are compiled into the image. To change one, edit the `env:` block at the top of the workflow and push. Only `NEXT_PUBLIC_WEBAPP_URL` can also change at runtime: `scripts/start.sh` rewrites it on boot. The rewrite replaces the built URL string wherever it appears, so `NEXT_PUBLIC_WEBSITE_URL` follows it only while the two build values are identical (both https://booking.flowko.si). Secrets are never build args. `NEXTAUTH_SECRET`, `CALENDSO_ENCRYPTION_KEY`, the `CALCOM_KEYRING_CREDENTIALS_*` keyring, the real `DATABASE_URL`, SMTP and Google credentials are set only on the host. This matters because the repository is public: `docker/build-push-action` then attaches a max-mode provenance attestation to the image, and that attestation records every build arg. The build starts its own throwaway Postgres, as upstream's release pipeline does.

Do not build on an Apple-Silicon Mac. The Dockerfile's builder stage is pinned to `$BUILDPLATFORM`, so a `--platform linux/amd64` build there ships arm64 native binaries.
