# Flowko fork of Cal.diy

This repository is Flowko's fork of [Cal.diy](https://github.com/calcom/cal.diy), the MIT community fork of Cal.com, self-hosted at https://booking.flowko.si.

## Upstream

Pinned to `calcom/cal.diy` commit `54343aa685ae8f33159d2f485ec4a57bad5c574a` (2026-09-20, "fix: restore @ts-expect-error for CacheProvider type mismatch (#30171)"). The `flowko` branch is that commit plus the changes below.

## Changes vs upstream

Lines marked *planned* are not on `flowko` yet; each is updated when its change merges.

- **U1 Slovenian rendering** (*planned*): `sl` locale enabled (`i18n.json` and the dayjs `sl` locale), with Slovenian dates in emails and booker month labels, and 24-hour email times for Slovenian recipients.
- **U2 Build pipeline**: upstream workflows and actions removed; `.github/workflows/build-image.yml` builds the image natively on linux/amd64 and pushes it to GHCR; the Dockerfile accepts the app name, company name, support address, sender name and signup lock as build args. `NEXT_PUBLIC_DISABLE_SIGNUP` now defaults to `true` in the Dockerfile, so every build, `docker compose` builds included, closes signup; pass `--build-arg NEXT_PUBLIC_DISABLE_SIGNUP=false` to reopen it.
- **U3 Auth hardening** (*planned*): no self-registration while signup is disabled, including through the magic-link email sign-in.
- **U4 Google privacy** (*planned*): Google profile scope removed, access revoked at Google on disconnect, known booker-PII log lines removed.
- **U5 Branding** (*planned*): Flowko name and assets in place of Cal.diy's.
- **U7b Platform hygiene** (*planned*): `scripts/seed-app-store.ts`, which `scripts/start.sh` runs on every boot, enables only `google-calendar` (from `GOOGLE_API_CREDENTIALS`). Every other app, Google Meet and the analytics and automation apps included, is created disabled, and the seed never changes the enabled flag of an existing row, so an admin's choice survives restarts. `yarn db-seed`/E2E (`scripts/seed.ts`) keeps upstream's behaviour. The `syncAppMeta` cron can now only disable apps, so a restart no longer switches off an app an admin enabled with missing keys. Booker details, calendar ids, webhook URLs and secrets, and credential keys are kept out of warn/error logs, and emails to the placeholder address of a phone-only booker are no longer sent. Reconnecting the same Google account replaces the earlier credential, a token discarded for missing scopes is revoked, and deleting an account revokes its Google grants first.
  - The seed never flips an existing row. On a database seeded before U7b, turn off Google Meet and the analytics and automation apps once under Settings → Admin → Apps.
  - After the first boot, `SELECT slug FROM "App" WHERE enabled;` should return only `google-calendar`.
- **U7d No seats or recurring series** (*planned*): `IS_SEATS_AND_RECURRING_ENABLED = false` in `packages/lib/constants.ts` turns off seated (`seatsPerTimeSlot`) and recurring (`recurringEvent`) event types. The event type create, update and duplicate handlers, which API v2 also calls, refuse to turn either on (turning them off still works). The booking service refuses a booking of a seated or recurring event type, a request that names a recurring series (a calendar's recurring event id included) or a seat, and a reschedule of a booking that still has seats or belongs to a recurring series; `/api/book/recurring-event` refuses every request. The Advanced tab's "Offer seats" setting and the Recurring tab are hidden. Cancelling existing bookings, seated ones included, is unchanged. Setting the constant to `true` restores upstream's behaviour; the seated and recurring E2E tests are skipped while it is `false`.
- **U8a Security**: cross-tenant reads, webhooks and disabled apps.
  - `viewer.availability.user` answers only for the caller's own username, and an `eventTypeId` only for an event type the caller has access to; a user with role `ADMIN` may read any user's availability.
  - Only a user with role `ADMIN` may list, read, create, edit, test or delete webhooks: every procedure of the webhook router refuses anyone else, and so do Zapier's and Make's subscription routes. The Webhooks settings entry, the webhook settings pages and the event type's Webhooks tab are hidden from non-admins. Webhook delivery is unchanged.
  - An app switched off under Settings → Admin → Apps stays off server-side. Event type create, update and duplicate, and the bulk update to the default conferencing app, refuse to turn a disabled app on in `metadata.apps` or to add its location (Google Meet, Cal Video, ...); an event type that already has one can still be saved, and turning an app off always works. A disabled app can't become a user's default conferencing app either. The booking page and the booking success page leave disabled apps out of the event type's metadata, so their tags are not loaded. `/api/integrations/*` refuses a disabled app's routes (its own add, callback and custom endpoints; U8c also stops Google Meet being installed through Google Calendar's callback).
  - Google Calendar's connect and OAuth callback go through `/api/integrations/*`, so `google-calendar` must be enabled under Settings → Admin → Apps before anyone can connect a calendar.
- **U8b Booker wording and cosmetics**:
  - The booking form no longer asks bookers to accept the app's terms. It says their details are processed by the app on behalf of the business they are booking with and links only the privacy policy (`booking_form_privacy_notice`, English and Slovenian). The signup page keeps `signing_up_terms`.
  - Every way of connecting Google Calendar (the Install and Connect buttons of the app store, onboarding and the calendar settings, the calendar settings' Add menu and the app installation's account step) first shows a notice of what Flowko reads and writes in the calendar, linking the privacy policy's section 3.3, and goes on to Google's consent screen only after Continue. Google's Workspace API user data policy asks for this disclosure right before the consent request. The notice (`google_calendar_connect_notice`, English and Slovenian) names the app as Google's consent screen does, "Flowko Rezervacije", and says it reads the calendar list and busy times of the chosen calendars and creates, updates and deletes only booking events. The name is written into the text, not taken from `NEXT_PUBLIC_APP_NAME`, so it must match the OAuth app name in Google Cloud Console.
  - Onboarding skips the plan step, whose team plan does not exist in this fork: `/onboarding/getting-started` still clears an earlier onboarding's details, then continues to personal onboarding, whose first step has no Back button.
  - The booker's layout toggle labels lose a stray `$`, the Host badge on the booking success pages is translated, and the login heading and the logo's alt text and title use `APP_NAME` instead of "Cal.diy".
- **U8c Security**: the 26 cross-tenant findings of the U8 audit, plus U8a's four review blockers.
  - *Booking uids:* a booking's uid comes from a CSPRNG, and so does the CalendarEvent builder's uid. They used to be uuidv5 of the tenant's username, the slot start and the creation millisecond, so an attacker could compute them, and a uid alone cancels a booking or shows it.
  - *Disabled apps fail closed:*
    - An `integrations:*` location type that maps to no enabled App row counts as a disabled app.
    - While `daily-video` is disabled, every Cal Video location books with no location and still sends its emails. That covers no location, a blank value, a conferencing default, a daily-video default, and an explicit or booker-sent `integrations:daily`. There are no Cal Video fallbacks.
    - `ensureAppsEnabled` also treats a new legacy `metadata.giphyThankYouPage` or a non-zero `price` as turning its app on.
    - Duplicating an event type that already holds such a value, or an unmapped `integrations:*` location, fails with `app_not_available_error`: the copy counts as new.
    - `daily-video` must never be enabled without valid Daily keys.
  - *Booker location:* a booking may use only a location the event type offers. `viewer.bookings.editLocation` refuses a disabled app's location, and a moved or confirmed booking does not keep one.
  - *Event types:*
    - `viewer.eventTypes.delete` authorizes the id it deletes.
    - Both event-type middlewares refuse an `id` and an `eventTypeId` that name different event types.
    - The delete and get input schemas are strict.
    - Duplicate refuses another tenant's personal event type.
    - Update, create and duplicate never write `parentId`, `teamId` or `profileId`.
    - Every schedule reference must be the caller's own schedule: `schedule`, `scheduleId`, `instantMeetingSchedule(Id)`, `hosts[].scheduleId` and the bulk default-availability update.
    - The webhook fan-out follows a parent event type only when it is a managed team event type, which never happens in this fork.
  - *Instance admin:* `isActiveInstanceAdmin` / `isActiveInstanceAdminSession` (`packages/features/auth/lib/isActiveInstanceAdmin.ts`) mirror the sign-in `validateRole`. An ADMIN signed in as `INACTIVE_ADMIN` (no 2FA, or a weak password) is not an admin on the server. That covers the webhook router, `availability.user`, the Zapier/Make subscriptions, `isAdminMiddleware`/`authedAdminProcedure`, and the admin and webhook settings pages. Every page under `settings/(admin-layout)` checks the admin itself, because an RSC partial render skips the layout. `adminFindById` selects no 2FA secret or backup code. `availability.user` is own-only and capped at 90 days.
  - *Webhooks:* the ownership middleware denies by default (a platform webhook: active admin only). SSRF:
    - self-hosted now runs the SaaS SSRF checks, unless `FLOWKO_ALLOW_PRIVATE_WEBHOOK_URLS=true` (exact value);
    - create, edit and test require https and resolve the hostname through DNS;
    - loopback, private, metadata and non-global-unicast targets are refused;
    - the test trigger times out after 10 s and doesn't follow redirects.
  - *`/api/link`:* the confirm/reject token uses AES-256-GCM with a key derived for this purpose (`symmetricEncryptAuthenticated`). `symmetricEncrypt`/`symmetricDecrypt` are unchanged, because they protect stored secrets. The route acts as the booking's organizer, and every bad token gets the same answer, so there is no padding oracle. Links in emails sent before U8c no longer work.
  - *Rate limits:* when `UNKEY_ROOT_KEY` is unset, `packages/lib/rateLimit.ts` counts the same limits in process, with bounded memory. A full store sends new keys to an overflow window and never evicts a live one.
    - The limiter is per process: set `UNKEY_ROOT_KEY` before running more than one replica.
    - Counters reset on every deploy.
    - `IP_BANLIST` must be a JSON array or unset, and it has no effect on callers that hash their identifier.
    - `NEXT_PUBLIC_IS_E2E` turns the limiter off (with the admin 2FA rule and Turnstile) and must never be set on Railway.
  - *Public procedures:*
    - `publicViewer.markHostAsNoShow` only reports a host no-show, only on an accepted booking that has started, and is limited per IP.
    - `checkIfUserEmailVerificationRequired` takes the session email from the session and is limited per IP.
  - *Google Calendar:* the OAuth callback requires a state nonce signed for the session user (403 otherwise), and `encodeOAuthState` always signs one. The add route refuses without `NEXTAUTH_SECRET`. Google Meet is installed from the calendar callback only while `google-meet` is enabled. The other apps' callbacks still treat state as optional: add the same check before enabling any of them.
  - *Selected calendars:*
    - `/api/availability/calendar` and `calendars.connectedCalendars` accept only the caller's own credential, event type and a calendar that credential lists.
    - The Google grant is kept on disconnect only when another user's live Google credential belongs to the same Google account.
    - Deleting a credential adds no Cal Video location while Cal Video is disabled.
  - *Intercom:* its script values are JSON-escaped. `apiKeys.create` refuses a disabled app.
  - *Bookings list:* `viewer.bookings.get` gives rows the caller doesn't organize a booker's view: no organizer id, no organizer email under `hideOrganizerEmail`, references reduced to `{type, meetingUrl, meetingPassword}`, no report, and only the caller's own phone number. `userIds` are authorized before any lookup.
  - *Public event data:* `getPublicEvent` returns no owner or host `metadata` or `defaultScheduleId`.
  - *Slot reservation is off:* `slots.reserveSlot` writes nothing and returns a fresh uid, `removeSelectedSlotMark` deletes nothing, and `getSchedule`/`isAvailable` ignore SelectedSlots. The public `getSchedule` drops `_enableTroubleshooter`, `_bypassCalendarBusyTimes` and `_silentCalendarFailures`.
- **U8d Security follow-ups** to U8c:
  - `getIP` ignores `cf-connecting-ip` and `true-client-ip` unless `TRUST_CLOUDFLARE_IP_HEADERS=true`, because there is no Cloudflare in front and the client can send those headers (live probe 2026-09-24). Otherwise the client IP is the first `x-forwarded-for` hop, which Railway's edge sets. Set the flag only behind Cloudflare with the origin locked to Cloudflare's IPs. Both flags are listed in `turbo.json` `globalEnv`.
  - Login limits, per David's decision:
    - 10 attempts per 60 s per typed email and client IP, checked before the user lookup;
    - 100 failed attempts per hour per account across all IPs (wrong password, or a wrong or missing TOTP or backup code). Once that is reached, the account is refused until the window resets.
    - A redeploy clears the windows, which is how the admin recovers early.
  - Email-code verification: `verifyCodeUnAuthenticated` runs a per-IP limit (10/60 s) before the per-email one when it is given the request. `sendVerifyEmailCode` also sends at most 5 codes per recipient in 10 minutes. A signed-in host may cancel 60 bookings a minute; anonymous cancel by uid stays at 10 a minute per IP.
  - Every webhook delivery re-checks the subscriber URL right before fetch: `sendPayload`, `WebhookService.sendWebhookDirectly` (BOOKING_REQUESTED through the tasker, and OOO), and the MEETING_STARTED/ENDED cron. A refused scheduled job is skipped and deleted. Refusals are logged without the URL. Zapier/Make `addSubscription` refuses such a URL.
  - The private-link hash and the password-reset link id come from a CSPRNG.
  - The legacy stripe `price` is gated on update and duplicate. Create's team-branch admin bypass uses the active-admin helper.
  - `handleConfirmation` gates the stored booking location, so a disabled app's location confirms as none. An offered-location refusal answers `location_not_offered_error` (en, sl).
  - `oAuth.updateClient`, `/auth/setup` and `/settings/license-key/new` use the active-admin helper.
  - tRPC's `errorConversionMiddleware` now really converts errors; it was dead code. A 4xx `HttpError` becomes its tRPC code, so a rate-limit denial is `TOO_MANY_REQUESTS`, and `ErrorWithCode` becomes its code. Only 5xx errors are reported, and the client does not retry `TOO_MANY_REQUESTS`.
  - A rate-limit refusal shows `rate_limit_exceeded` in the user's language on the booking form, the login, forgot-password and new-password views, and the host no-show toast. Report is offered only to the booking's host. Onboarding says a disabled conferencing app is not available.
  - The `/apps/installation` page no longer selects the App row's `keys`, which for google-calendar hold the platform's OAuth client_secret and reached any signed-in tenant through the page props (found by the U8 re-attack). The public email-code check passes its request, so its per-IP limit runs, and a limit refusal stays a 429. A missing or non-string email or password gets the unknown-email answer before any lookup, and `authorizeCredentials` no longer logs the credentials.
  - A hidden event type's private link (`/d/<hash>/...`) is a convenience, not access control: in this code anyone who knows the slug can still book it. Don't promise a client that a private link keeps an event type private.
- **U9 Google Calendar app page and copy**:
  - `/apps/google-calendar` shows Flowko as publisher (https://flowko.si/, rezervacije@flowko.si) and a Slovenian description (`googlecalendar/_metadata.ts`, `DESCRIPTION.md`). Like the connect notice, it says the app reads the calendar list (`calendarList.list`) and the busy times of the chosen calendars, creates, updates and deletes only booking events, and does not read the contents of other events. That holds only while the calendar-subscription features stay off (see below).
  - `DESCRIPTION.md` has no front-matter, so the page has no screenshot gallery, and `googlecalendar/static` holds only `icon.svg` (pinned by `static.test.ts`). Upstream's `GCal1.png`/`GCal2.png` showed Cal.com's own calendar with real people's calendar names, and `copy-app-store-static.js` serves everything in `static/` publicly. Add Flowko screenshots taken on a demo account without third-party data back as `items:` front-matter only.
  - Every app page (`/apps/<slug>`) drops upstream's footer ("every app is open source and peer reviewed", the "Report app" mailto): a single-operator service has no app review. The category chip shows the translated category (sl "Koledar") and falls back to the raw id for a category without a key.
  - `WEBSITE_PRIVACY_POLICY_URL` and `WEBSITE_TERMS_URL` fall back to https://flowko.si/privacy and https://flowko.si/terms when their build args are missing.
  - On connect, the Google callback selects the primary calendar for conflict checks, and the primary calendar is the default destination for booking events. Hosts change both under Apps → Installed apps → Calendars.
- **U9 Unreadable Google calendars fail closed**: a calendar Flowko can't read is unknown, not free.
  - *Free/busy errors:* Google's freebusy answers a calendar it could not read (deleted, no longer shared, a Google backend error) with `errors[]` and an empty `busy[]`, which upstream counted as free time. Now `GoogleCalendarFreeBusyError` is thrown for any calendar or group with errors, on every free/busy path (single and chunked ranges, the time-zone variant, the primary fallback). `getBusyCalendarTimes` returns `success: false` and `getBusyTimes` throws, so the slots query answers normally with no slots (`getUserAvailability` returns `dateRanges: []`) and a booking is refused (`NoAvailableUsersFound`). Ranges longer than 90 days are asked in contiguous 90-day chunks up to the exact end, and a chunk answered without calendars fails the same way instead of being skipped. A requested calendar missing from Google's answer is only logged, as a count. Logs carry Google's reasons and counts, never calendar ids.
  - *Several Google connections:* every connection of a host is asked for all of the host's selected Google calendars. A connection skips the error for a calendar selected under another connection, because that connection reads the calendar and fails closed on it itself. Errors for its own calendars, for rows without a credential, for the fallback primary and for groups always fail. Delegation credentials skip nothing.
  - *Invalid connections:* a connection whose refresh token Google rejects (`invalid_grant`: access revoked, or the 7-day refresh-token expiry while the OAuth app is in Testing mode) is marked `Credential.invalid`. Upstream then skipped it, so the calendars selected under it looked free. Now `getCalendarsEvents` and `getCalendarsEventsWithTimezones` throw `InvalidCalendarCredentialError` while an invalid calendar credential still owns a selected calendar in scope (by `credentialId`; a legacy row without one counts only when no valid credential of its kind reads it): no slots, no bookings. An invalid credential without selected calendars stays skipped. The log carries credential ids and a count.
  - *Host e-mail:* `invalidateCredential` flips a credential once (`updateMany` on the id and `invalid` false or null; mail only when `count === 1`) and sends the host one `BrokenCalendarConnectionEmail` in their locale (sl subject "Povezava z Google Calendar ne deluje", linking `/apps/installed/calendar`). The e-mail kill switch applies, and team, delegated and non-calendar credentials get no mail. The host also sees the existing banner for apps with invalid credentials ("Znova namesti aplikacijo"). `Credential.invalid` never clears by itself (upstream `OAuthManager` TODO).
  - *Reconnect:* the callback's `replaceEarlierGoogleCalendarCredentials` treats a credential marked invalid like a revoked grant when Google's lookup is inconclusive, and still replaces it only when the old credential used the new primary calendar and the new connection keeps every calendar it had. Otherwise the old credential stays and blocks until the host removes it with "Odstrani aplikacijo" (`handleDeleteCredential` works on a dead token; the cascade deletes its selected calendars).
  - *Runbook:* a host with no slots and the warn log "Google Calendar could not read the free/busy of N calendar(s): notFound" has a selected calendar that was deleted or unshared in Google; until a recovery patch ships, delete that `SelectedCalendar` row. A host with no slots and "Refusing availability: an invalid calendar credential still has selected calendars" must reconnect Google or remove the old connection.
- **U9 Tokens encrypted at rest**: Google's OAuth policy requires OAuth tokens encrypted at rest. Upstream kept the token object in plaintext in `Credential.key`. Its optional keyring copy in `encryptedKey` swallowed encryption errors, and its only decrypting reader fell back to the plaintext key.
  - *Storage:* a `google_calendar` credential (and `google_video`, if it is ever enabled) keeps `{"_enc":"keyring-v1"}` in `key`, and in `encryptedKey` the JSON of an AES-256-GCM envelope `{v:1, alg:"AES-256-GCM", ring:"CREDENTIALS", kid, nonce, ct, tag}` (base64url; 12-byte nonce, 16-byte tag) of the token object. The AAD binds the purpose `Credential.key`, `type`, `userId` and `teamId` (built only by `credentialKeyAad()`), so an envelope copied to another row or tenant fails authentication. Envelopes are validated (v, alg, ring, an upper-case kid, nonce and tag lengths) before any key material is read. `schema.prisma` is unchanged; plaintext rows are refused, never read as a fallback, and never migrated.
  - *Where tokens are decrypted:* only in `CalendarAuth` (lazily, when a Google call needs them) and at the revoke and account-lookup sites of `handleDeleteCredential` and `replaceEarlierCredentials`. The code is in `packages/features/credentials/services/CredentialDataService.ts` and `packages/lib/crypto/keyring.ts`. The refresh write-back re-encrypts with the CURRENT kid (`CredentialRepository.updateEncryptedKeyWhereId`). It binds the envelope to the row's type, userId and teamId as it reads them just before the write, not to the fields the token was decrypted under, and writes only while the row still has them. A DB write that re-points a row to another user between that read and a refresh would store the old owner's refreshed token, encrypted for the new owner, in that row; this is an accepted risk, because it needs DB write access and a race. No token is copied back into an in-memory `credential.key`. The fail-open decrypt in `getCalendarsEvents` is gone. `updateTokenObjectInDb` also serves the disabled pipedrive app, which would now store an encrypted key its own reader can't use.
  - *Fail closed:* every failure raises `CredentialKeyUnavailableError` with a reason: `keyring_not_configured` or `decrypt_failed` (transient), `not_encrypted` or `malformed_envelope` (permanent). It is logged once per credential and reason every 5 minutes as `Credential key unavailable (<reason>) for credential <id|new> (<type>)`, with the credential id, type and reason and the envelope's kid (a new credential's line carries the userId instead). The kid is not secret. The line never carries a token, the envelope's nonce, ciphertext or tag, an env value or an error object. A key failure never marks a credential invalid and never sends the broken-connection e-mail.
    - Connect: `add` answers 503 before Google's consent screen, and the callback answers 503 before the code exchange. If storing fails after the exchange (after the keyring pre-flight, practically only a DB error), no row is created and the fresh grant is revoked, best effort: `revokeUnstoredGoogleCalendarToken` keeps the grant when Google's account lookup is inconclusive, or when another credential may share it (any other Google Calendar connection of the same user, even for another Google account, or another user's connection that Google confirms is the same account).
    - Availability: that host's whole range is busy, so no slot is offered; other tenants are unaffected. Where a booking still goes through (a create, reschedule or cancel), its Google event is missing or stale and the failure is logged. While the keyring is down, the host's Settings → Calendars shows the generic `calendar_error` hint to reconnect with all permissions, although a reconnect answers 503 and a removal is refused; no e-mail is sent.
    - Refresh: nothing is written, and the refreshed access token is discarded.
    - Disconnect: refused ("try again later") while the failure is transient, so the Google grant is still revoked once the key is back. With a permanent failure the row is deleted without a revoke, and the credential id and reason are logged. Unchanged from upstream: disconnecting a connection whose grant Google already revoked, but which is not marked invalid yet, can send the host the broken-connection e-mail ("reconnect it") while they remove it, because the disconnect still lists the calendars first and that marks the credential invalid.
    - Account deletion never blocks: an undecryptable credential's revoke is skipped with an error log.
    - `viewer.apps.updateAppCredentials` refuses (`FORBIDDEN`) a credential that has an `encryptedKey` or is not a paypal, alby, hitpay or btcpayserver credential.
  - *DB backstop:* migration `20260925120000_flowko_credential_no_plaintext_oauth_tokens` adds the trigger `flowko_credential_key_guard` (BEFORE INSERT OR UPDATE on `"Credential"`, for each row, function `flowko_credential_key_guard()`), set `ENABLE ALWAYS` so that it also fires under `session_replication_role = replica`. Whatever the code path, it refuses an INSERT or UPDATE that:
    - puts a token field into `key`: `"key"::text !~* '(access_?token|refresh_?token|id_?token)'`, so in any case and with or without the underscore (`access_token`, `accessToken`, `ID_TOKEN`), as a name or inside a value, nested ones included. No other app's stored key matches: the payment apps' keys, the key-less apps' `{}`, the hex strings of CalDAV, Apple, Exchange and ICS, and sendgrid's `{encrypted}` all pass. The pattern also matches words such as `invalid_token`, which no app stores.
    - leaves a `google_calendar` or `google_video` row whose `key` is not exactly `{"_enc":"keyring-v1"}`, or whose `encryptedKey` is NULL or empty.
    - A refused write fails with SQLSTATE 23514 and the fixed message "Credential write refused: OAuth token field in key, or invalid encrypted Google credential shape", with no DETAIL or HINT and nothing from the row. It is a trigger, not a CHECK, because a CHECK violation's DETAIL ("Failing row contains (...)") would copy the refused token into the app and Postgres logs. The migration first counts the existing rows that break these rules and, if there are any, fails (P0001) before creating anything.
    - The writers that now fail there are all off on this instance: other apps' OAuth callbacks and refreshes, `markTokenAsExpired` (credential sync), the app-credential webhook, delegation write-backs, Google Meet's own add route (`googlevideo/api/_getAdd.ts` stores `{}` without an envelope; installing Meet through the Google Calendar callback encrypts), the dev seed's Google fixture (`E2E_TEST_CALCOM_QA_GCAL_CREDENTIALS`), and upstream E2E and integration-test fixtures that store tokens in `key` or a bare `{}` in a Google row. **Enabling any other OAuth app, Google Meet, Google or Outlook login, credential sync or delegation first needs U9 extended to it.**
    - If SQLSTATE 23514 on `"Credential"` ever appears in the app or Postgres logs, some code path tried to store a token in `key` or a malformed Google row. The trigger's error carries nothing from the row, and Prisma sends values as bind parameters, which Postgres logs only with non-default settings: `log_statement` must stay `none` and `log_parameter_max_length_on_error` `0`. Still check the surrounding log lines for a token. If in doubt, treat that grant as exposed: revoke it at Google and have the tenant reconnect. Then find and fix the writer.
  - *Keyring variables* (host-only: never a build arg or `NEXT_PUBLIC_`). `turbo.json` passes `CALCOM_KEYRING_CREDENTIALS_*` through with `globalPassThroughEnv`. Without that, Turbo's strict env mode strips them from `turbo run start` (the container's `yarn start`), and every Google connect and read fails closed. Passthrough keeps the key out of Turbo's task hashes.
    - `CALCOM_KEYRING_CREDENTIALS_CURRENT` names the kid that new writes use. It must be upper-case and match `/^[A-Z0-9_]{1,32}$/` (e.g. `K1`). A lower-case or otherwise invalid value counts as not configured: connect answers 503 and nothing is written.
    - `CALCOM_KEYRING_CREDENTIALS_<KID>` (e.g. `CALCOM_KEYRING_CREDENTIALS_K1`) is 32 random bytes in base64url without padding (43 characters), distinct from `CALENDSO_ENCRYPTION_KEY` and `NEXTAUTH_SECRET`. Generate it into a file, never onto the screen: `node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64url'))" > "$KEYFILE"`, then set it from that file (`railway variable set … --stdin < "$KEYFILE"`) and delete the file. Never commit, log or paste the value.
    - The operator runbook (generate, back up, set, check the backup, restore, rotate) lives in Flowko's private operations notes, not in this public repository. A key lost from both the host and its backup leaks nothing, but every tenant must reconnect Google.
    - What it protects against: database dumps, backups, replicas and a database-only compromise. It does not protect against anyone who can read the host's variables or run code in the web process (the same trust boundary as `DATABASE_URL`). Out of scope: NextAuth `Account` tokens (Google, Azure and SAML login are off), the Google `client_secret` in `App.keys` and `DelegationCredential.serviceAccountKey`.
  - *Rotation:* set the new kid's variable, then point `CURRENT` at it. Rows move to the new kid on their next token refresh. While `CURRENT` names a kid whose variable is missing (the old kid still set), reads work until a token needs a refresh; from then on each Google call of that host asks Google for a new token and fails to store it, so it fails closed, and nothing is stored or marked invalid. The `add` pre-flight answering 503 is the quickest signal of this state. **Never delete a kid's variable while the kid census still shows rows for that kid**: such a row reads as `keyring_not_configured` or `decrypt_failed`, both transient, so its disconnect is refused, a reconnect keeps it and its host has no slots. Re-encrypt dormant rows, or have their tenants reconnect or remove Google, while the old key is still set. Keep a retired key's backup for at least 7 days after its census reaches 0, because the daily database backups still hold its envelopes. Kid census:
    ```sql
    SELECT "encryptedKey"::jsonb->>'kid' AS kid, count(*) FROM "Credential" WHERE "encryptedKey" IS NOT NULL GROUP BY 1;
    ```
  - *A Google credential stuck on a retired or corrupted key* can't be removed from the UI. An operator removes it:
    1. Revoke the grant in the tenant's Google account (myaccount.google.com/connections).
    2. Delete the `Credential` row by id. The cascade removes its selected calendars.
  - *Verification* (prints no secrets):
    - Before the deploy, this must return 0, or the migration's pre-check fails it:
      ```sql
      SELECT count(*) FROM "Credential"
      WHERE NOT coalesce("key"::text !~* '(access_?token|refresh_?token|id_?token)'
        AND ("type" NOT IN ('google_calendar', 'google_video')
          OR ("key" = '{"_enc":"keyring-v1"}'::jsonb AND "encryptedKey" IS NOT NULL AND "encryptedKey" <> '')), false);
      ```
    - After the deploy, the trigger must exist and be enabled. This check is mandatory: `scripts/start.sh` has no `set -e`, so a failed migration still boots the app, without the trigger, and blocks every later migration (P3009). Expect `applied=t` and `not_rolled_back=t`, then one row with `tgenabled = A` (always) and `tgtype = 23` (row, before, insert, update).
      ```sql
      SELECT migration_name, finished_at IS NOT NULL AS applied, rolled_back_at IS NULL AS not_rolled_back
      FROM "_prisma_migrations" WHERE migration_name LIKE '%flowko_credential_no_plaintext_oauth_tokens';
      SELECT tgname, tgenabled, tgtype FROM pg_trigger
      WHERE tgrelid = '"Credential"'::regclass AND tgname = 'flowko_credential_key_guard';
      ```
    - Signed in, `GET /api/integrations/googlecalendar/add` answers 200 with a `url` when the keyring reached the process, and 503 when it did not (for example, Turbo stripped the variables).
    - Standing invariants, both 0 after any connect or refresh:
      ```sql
      SELECT count(*) FILTER (WHERE type IN ('google_calendar', 'google_video')
               AND ("key" <> '{"_enc":"keyring-v1"}'::jsonb OR coalesce("encryptedKey", '') = '')) AS google_rows_not_encrypted,
             count(*) FILTER (WHERE "key"::text ~* '(access_?token|refresh_?token|id_?token)') AS rows_with_token_fields
      FROM "Credential";
      ```
  - *Rollback:* an image without U9 can't parse the placeholder, so after a Google connect a rollback breaks Google for those tenants (nothing leaks), and the trigger refuses its plaintext writes. Roll forward instead. If a rollback can't be avoided:
    1. Disconnect every Google credential with the U9 image first (it revokes through decryption).
    2. Drop the trigger by hand: `DROP TRIGGER IF EXISTS "flowko_credential_key_guard" ON "Credential"; DROP FUNCTION IF EXISTS "flowko_credential_key_guard"();`
    3. To roll forward again, first disconnect with the old image every Google connection it made: the old image revokes them, while the U9 image would delete them without a revoke. The pre-deploy query above must then return 0.
    4. The roll-forward does not re-create the trigger, and nothing reports that: `_prisma_migrations` still records `20260925120000_flowko_credential_no_plaintext_oauth_tokens` as applied, and `prisma migrate deploy` applies only unrecorded migrations. The code still encrypts; only the DB guard is gone. Rerun the migration's `migration.sql` by hand, in one transaction that stops at the first error (`psql -v ON_ERROR_STOP=1 --single-transaction -f migration.sql`; it can be rerun safely), then rerun the `pg_trigger` query above.

## API v2 must not be deployed

The image builds only the web app (`./Dockerfile`); `apps/api/v2` (the `calcom-api` service in `docker-compose.yml`) is not part of the deployment and must stay out of it. Flowko's booker-facing fixes were made on the web app's routes and pages, not on API v2. There, `GET /v2/bookings/:bookingUid` (2024-04-15, no auth guard on the route) returns every seat's reference, and the 2024-08-13 `GET /v2/bookings/:bookingUid` and `/v2/bookings/by-seat/:seatUid` (optional auth) return every attendee's `seatUid` when the event type shows attendees. A seat's reference cancels that seat through `POST /v2/bookings/:bookingUid/cancel`. Deploying API v2 first needs an auth guard on those routes, or their output limited to the caller's own seat. It would also reopen U8c fixes that live only on the web app's tRPC routes: API v2 has its own SelectedSlots writers (slot reservation, AV-2) and accepts the internal `getSchedule` flags (AV-5), and its throttler keys on the client-sent `cf-connecting-ip` (`apps/api/v2/src/lib/throttler-guard.ts`).

## Calendar-subscription features must stay off

Keep the `calendar-subscription-cache` and `calendar-subscription-sync` features off (Settings → Admin → Features, `/settings/admin/flags`). When they are on, `packages/features/calendar-subscription/adapters/GoogleCalendarSubscription.adapter.ts` calls `events.list` on the selected calendars and stores the summary, description and location of every event. It is the only reader of event contents, so turning it on makes the connect notice ("does not read the contents of your other events"), the Google Calendar app page description and section 3.3 of the privacy policy false. `SELECT slug, enabled FROM "Feature" WHERE slug IN ('calendar-subscription-cache','calendar-subscription-sync');` must return no row with `enabled = t`.

## One-time GitHub setup

The fork's default branch is still `main`, which carries all of upstream's workflows, eleven of them scheduled (two run every minute). GitHub runs scheduled workflows only from the default branch, and shows the "Run workflow" button only for workflows on the default branch. These are repository settings, so the owner does them once, in this order:

1. Push the `flowko` branch.
2. Settings → General → Default branch: switch to `flowko`. Alternatively, push a commit to `main` that deletes `.github/workflows`.
3. Only then enable GitHub Actions for the fork in its Actions tab.
4. Start the first build by pushing a commit to `flowko`.

## Rebuilding the image

Every push to `flowko` runs `.github/workflows/build-image.yml` on a GitHub-hosted `ubuntu-latest` runner. Once `flowko` is the default branch, it can also be run by hand from Actions → Build image → Run workflow on `flowko` (any other branch is skipped). It pushes:

- `ghcr.io/davidvojvodic/flowko-booking:<commit sha>`, which is the tag to deploy
- `ghcr.io/davidvojvodic/flowko-booking:flowko-latest`

The workflow does not boot the image before pushing it (upstream's release pipeline does), so `flowko-latest` is untested. Deploy only a `<commit sha>` tag that has been started and checked.

The `NEXT_PUBLIC_*` values are compiled into the image. To change one, edit the `env:` block at the top of the workflow and push. Only `NEXT_PUBLIC_WEBAPP_URL` can also change at runtime: `scripts/start.sh` rewrites it on boot. The rewrite replaces the built URL string wherever it appears, so `NEXT_PUBLIC_WEBSITE_URL` follows it only while the two build values are identical (both https://booking.flowko.si). Secrets are never build args. `NEXTAUTH_SECRET`, `CALENDSO_ENCRYPTION_KEY`, the `CALCOM_KEYRING_CREDENTIALS_*` keyring, the real `DATABASE_URL`, SMTP and Google credentials are set only on the host. This matters because the repository is public: `docker/build-push-action` then attaches a max-mode provenance attestation to the image, and that attestation records every build arg. The build starts its own throwaway Postgres, as upstream's release pipeline does.

Do not build on an Apple-Silicon Mac. The Dockerfile's builder stage is pinned to `$BUILDPLATFORM`, so a `--platform linux/amd64` build there ships arm64 native binaries.

After the first push, check the GHCR package's visibility. A private package needs a token with `read:packages` on the deployment host.
